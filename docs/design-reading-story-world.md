# 比赛版设计：安的共读书房与故事分支

> 状态：2026-09-08 初版设计；已完成其中部分短篇原型，并非全文实现。
> 2026-09-09 更新：产品主入口调整为“先伴读理解，再自愿改写”，见 [伴读与读后分支设计](design-reading-companion.md)。本文保留故事世界与分支的底层契约；旧主流程、首发样本和阶段安排不再作为最新产品计划。
> 开发分支：`codex/vibecoding-reading-showcase`，起点 `974d4e4`；使用独立 worktree，避免并行评估任务切换分支造成混写。
> 赛道：生活工具。作品提交节点：2026-09-14，具体截止时刻待活动方确认。
> 本文定义比赛版本，不表示现有生产能力已经满足这些契约，也不授权部署或修改正式记忆。

## 1. 产品目标与可演示效果

用户提供一本故事书，安读取并整理人物、事件、核心场景和证据，建立故事知识图谱。用户选择某个场景中的人物，与只拥有当时认知的他交谈；交互可能改变信任、认知或行动，形成能够继续发展的新故事线。

主体验：**放入书籍 → 看安解读 → 浏览故事地图 → 进入场景 → 与人物交谈 → 观察变化 → 沿新分支继续。**

比赛版必须展示三种事实：

1. 阅读事实：某条判断来自实际读过的哪个段落，安有哪些疑问或修订。
2. 认知事实：同一事件，不同人物知道、相信和误解的内容不同。
3. 行为事实：用户参与形成的新经历，改变了后续人物回应或事件走向。

不以节点数量、流水线完成状态或 Critic 通过代替体验验收。公开解读展示原文、结构化解释、备选解释、结论变化与动作回执，不展示隐藏思维过程。

### 1.1 首发范围

- 以一篇自写或有合法使用权的短篇为主样本，5–8 个核心场景、2–3 个主要人物。
- 至少包括一项秘密、一次误解、一个可改变的决定，以及一个互动后续场景。
- 支持书籍导入与后台解读；演示同时提供预先真实解读完成的样本，不让观众等待整本书处理。
- 第一版不承诺任意长篇均能自动产出稳定可玩世界；未准备好的场景保留“待核验”。
- 一个故事分支中同一时刻只激活一个人物，但可在场景允许时切换人物。
- 不做多人同时扮演、开放世界无限演化、语音、OCR、复杂战斗或资源经济。

### 1.2 固定演示样本

虚构故事《未送达的信》（工作标题）：姐姐藏起朋友写给弟弟的信，弟弟误以为被朋友遗忘，准备乘末班船离开。

在离港场景与弟弟交谈：

- 初始时他不知道藏信，也不应凭读者的全书视角知道。
- 用户说“姐姐藏了信”，首先形成一条听闻，不自动成为他确信的事实。
- 用户引导他去核实，人物可以选择等待、追问或拒绝。
- 若弟弟留下，原著“离港之后”的未来不再自动生效。
- 切换到姐姐时，她知道自己藏信，但不知道另一段私下对话，除非发生告知或观察事件。
- 进入下一场景后，弟弟记得互动，回应与原著线不同；原著仍可独立查看。

## 3. 核心认知契约

### 3.1 三种视角

- **世界事实**：事件实际是否发生；包括原著事实与当前分支已提交事件。
- **人物认知**：人物亲历、观察、听闻、推断、误解、怀疑的内容。
- **读者视角**：用户目前允许查看的原文、解读和剧透范围。

事件发生不代表所有人物知道；人物听说也不代表世界事实被改变。人物可以持有与真实事实相反的信念，这不是需要自动纠正的数据错误。

未知描述不得泄露答案：向弟弟注入“你不知道姐姐藏了信”已经泄密，应只注入“你还没有收到回信，不清楚原因”。完整秘密与“谁不知道什么”的对照表只给安和允许查看的读者。

### 3.2 两种顺序

- `narrative_order`：文本揭示顺序，用于读者进度和来源定位。
- `happened_before/after`：故事内发生顺序，用于人物经历与场景推进。
- `learned_at`：人物获得某信息的事件位置，可晚于事件发生时间。
- 不强行给模糊时间赋确切日期；并行/不确定事件允许部分顺序，场景推进用前置条件决定。
- 用户默认进入场景开始时；场景结束后的事件不会提前加入记忆。已命名的中途节点可以单独成为可进入锚点。

### 3.3 原文、推断与创作

统一来源分类：`canonical`（原文明示）、`inferred`（有原文依据的解释）、`simulated`（互动生成）。推断需保留依据、替代解释、置信等级；生成内容需关联互动事件。

合法推断可以支持人物的当下表现，无需把每一次新回应都先证明为原作者写过的话。但不得伪装成原文引语或既有经历。原著已发生的事实与本分支新事件各自保留来源。

### 3.4 可改变性

按事件和选择评估，场景卡汇总展示，避免单一“可改变/不可改变”覆盖整个场景：

- `fixed_past`：当前进入点之前已发生的事实；要改需另选更早的分岔点。
- `open_choice`：人物尚可做出的选择，可以影响。
- `world_constraint`：世界设定或物理条件；说服人物不能直接改写。
- `conditional_future`：原著未来，依赖某些前提，不是当前分支已经发生的事。

安评估可干预空间、改变阻力、后续影响，采用低/中/高及短理由与证据。阻力是辅助判断，不是固定成功概率。语义决策由模型结合人物与情境完成；系统只校验既定事实、权限、版本和前置条件。

## 4. 数据模型与事实源

新增 `internal/story` 作为领域模块，调用现有阅读、模型、队列和语料能力；避免在 RoleDefinition 上继续叠加完整故事世界。

| 对象 | 关键内容 |
| --- | --- |
| StoryBook | book_id、owner_scope、文档/版本、内容哈希、阅读与编译状态 |
| EvidenceSpan | document/chunk、字符起止、原文哈希、章节/页码；精确支持范围 |
| StoryCharacter | 人物ID、别名、角色模型模板；具体时期状态由快照覆盖 |
| StoryScene | 场景ID、叙述顺序、世界内顺序约束、地点、参与者、进入条件、进入/退出锚点 |
| StoryEvent | 事件ID、主体/对象、前置条件、后果、发生位置、来源分类与证据 |
| CharacterKnowledge | 命题、知道/相信/怀疑、获得方式、learned_at、来源事件、替代/撤销关系 |
| CharacterSituation | 当下目标、情绪、关系、可感知环境、尚待选择事项、适用场景与依据 |
| StoryInterpretation | 安的短判断/疑问、证据、解释类型、替代解释、版本变化 |
| StoryBranch | book_version、owner、parent_branch、fork_scene、parent_head_at_fork、head_revision |
| StorySession | owner、branch、当前场景/人物、用户在场身份、阅读可见范围、状态 |
| StoryTurn | turn_id、idempotency_key、input_revision、回答、候选后果、提交状态 |
| StoryMutation | 事件、人物认知/关系增量、before/after、原因码、来源turn、撤销关系 |
| CharacterSnapshot | branch/revision/scene/character、实际注入的认知与依据、状态、内容哈希 |

文件为事实源，目录拟为 `data/memory/stories/<owner>/<book_id>/`，包含不可变 book_versions、interpretations、branches、turns 与 commits。用户资料目录/正文沿用 0700/0600；原文不进入 Git。

复用 SQLite FTS5 原文索引；为故事建立明确的 corpus namespace，而不是创建一个假人物来持有整本书。Neo4j 作为可重建投影，记录 Book、Scene、Event、Character、CharacterState、Branch 及 SUPPORTED_BY、PRECEDES、CAUSES、PARTICIPATES、LEARNS、FORKED_FROM 等关系。

图中 CAUSES 是有来源的解释，不把时间相邻自动当作因果。节点按书、拥有者、分支和版本查询；默认只展开当前场景的一跳关系。图暂时不可用时由文件生成同形读模型，不能阻断阅读与交互。

## 5. 从书籍到可进入场景

解读状态机：`imported → reading → extracting → reconciling → validating → ready`，各阶段支持 paused、failed、cancelled 和 checkpoint。

1. **导入**：校验文档、内容去重、建立章节与精确段落位置；文本、Markdown、带文本层PDF复用已有能力。
2. **逐章阅读**：复用真实阅读回执，提取事件、人物、知情范围和疑问。按模型实际配置分批，不能假定模型一定有百万上下文。
3. **场景编译**：根据时间、地点、参与者或核心冲突变化整理场景；章节不必等于场景。
4. **跨章对齐**：人物别名合并，区分事发与揭示顺序，整理因果与每个人的获知事件。
5. **人物视角重建**：依据事件与获知记录计算阶段快照，禁止让后文结论倒灌到早期人物。
6. **校验**：引用存在、时间不矛盾、场景前置条件可达、人物信息来源合理。歧义保留为未解决或可选解释。
7. **发布解读版本**：全书可以部分 ready；只开放检查通过的场景，未解决的关键秘密/时序冲突场景不可进入。

Compiler 和 Critic 都按 EvidenceSpan 获得完整被引内容与必要上下文。证据超出预算时分批审查或按ID读取，不能截掉引用所在后半段再宣判“无依据”；未核验应明确为 pending。

自动研究以书为起点，不强制先联网。外部资料只在版本、背景或解释存在明确缺口时由安提出查询并执行已有预算策略；候选先比较相关性再读取，无结果时可调整查询。读者能查看采用/排除情况。外部解读不能覆盖原文，也不自动变为人物经历。

书籍修改或重解读产生新 book_version；已存在分支固定使用旧版本，避免重新编译使正在交互的故事悄悄改变。

## 6. 人物运行时与信息边界

`BuildCharacterSnapshot(owner, book_version, branch, revision, scene_anchor, character)` 是唯一角色上下文入口：

1. 获取截至分岔点的原著已发生事件和当前分支已提交事件。
2. 根据人物的观察、听闻与推断记录计算已知/信念及当下处境。
3. 加入该人物当时成立的身份、语言特点与关系；不能注入全书综合人格中含未来经历的描述。
4. 加入该会话近期可见对话与更早互动摘要，保留事件引用。
5. 提供默认认知快照，并允许工具展开已授权的个人经历。

过滤在索引候选生成之前执行，覆盖候选标题、摘要、计数、正文、缓存、Timeline、Claims、STM压缩和工具输出。缓存键至少包含 owner/book_version/branch/revision/scene/character。

故事 Actor 使用专用工具：`get_character_situation`、`search_character_experiences`、`read_character_experience`。同一原文段落可能混有旁白秘密与角色亲历，不能把整个 Chunk 当作角色可读单位；Actor 只获得经过认知授权的命题/经历投影。完整原文 EvidenceSpan 由安和读者证据面板查看，书内被角色实际读到的信件等例外也需显式授权。

已有 `search_book_passages/read_book_passage` 不直接注册到故事 Actor；普通角色原有行为继续兼容。

切换角色、场景回退、新分支、重新开始均创建或选择匹配的会话快照，不复用含未来信息的 STM。人物不会收到安的后台解释、其他人物私聊和读者证据面板内容。

大模型可能凭预训练知道知名故事结局；输入隔离不能从模型参数中抹去此知识。须在提示和输出检查中约束人物视角，并分别测试受控陌生故事和熟悉故事。不得宣称所有名著完全零剧透已被结构校验保证。

## 7. 对话、裁定与分支推进

### 7.1 用户在故事中的位置

进入时默认用户是“此处可与人物交谈的来访者”，明确当前可进行交谈/建议/出示已有物品，不默认拥有上帝式改写能力。后台讨论与台前发言分开；用户打开证据面板不会自动把信息告诉人物。

每次进入均创建用户私有探索分支，最初只继承原著到当前锚点的事实。原著是不可变参照。所有交谈都保留为分支事件；首次发生有意义的认知/关系/行动偏离时标记“故事开始分岔”，无需每句话产生一个新分支。

### 7.2 一轮交互的提交协议

1. 校验拥有者、活动人物、场景、幂等键与期望 revision，构建人物快照。
2. Actor 生成对话与可选行动意图；行动意图此时尚未改变世界。
3. 安读取世界状态和本轮内容，输出短公开解读与结构化后果：`no_material_change / knowledge_update / relationship_update / action / scene_transition`，可组合。
4. 验证受影响人物、前置条件、来源、事实边界和版本；不合法时允许一次有界修订，仍失败则保留失败回执，世界状态不前进。
5. 需要时修正角色最终回复，使它与获准后果一致。例如“我打算去找姐姐”不等于已经找到。
6. 以一个故事事务提交回答、事件与所有受影响人物增量，之后生成 Episode/图谱投影。
7. UI 展示已提交回答、可核验变化和下一场景选项。

第一版回复先缓冲并检查，再作为完成内容显示；等待时展示真实阶段事件。不要把已经向用户播放的泄密文字声称为可撤回。若未来加入文本流式，应明确草稿状态且仍不能泄露未授权内容。

`heard(user_claim)` 与 `believes(claim)` 分开。用户声称拥有物品、已经做过事或透露原著秘密，必须按当前世界状态和人物反应裁定，不能通过一句话获得不存在的道具或改变旧历史。人物可以质疑、拒绝、提出交换条件；不为达成剧情分叉保证说服成功。

### 7.3 分支与因果

新分支只继承父分支在 `parent_head_at_fork` 之前的事件。父分支后续新增内容不得渗入；不采用“允许读取所有祖先世界线的全部记忆”的实现。

互动改变事件前置条件后，安列出受影响的原著未来：`still_possible / blocked / uncertain`。原著未来不自动执行；续写必须基于当前分支状态。

用户点击“继续故事”时生成一个有界后续场景：环境、参与人物、短事件、可进入人物与认知更新。检查人物出场、物品位置、获知渠道与事件因果一致后提交。初版每次生成一个场景，避免无界后台续写。

### 7.4 存档、撤销与恢复

- append-only 事件与 Mutation 记录；多个角色共享 StoryBranch 的 head revision。
- 文件提交采用事务包：先写完整不可变 commit bundle，再在分支锁内校验旧 head 并原子切换 manifest；切换前失败无可见增量，切换后重复请求返回原结果。
- 图谱、Episode、缓存通过提交后 outbox 幂等更新，可重试且不充当事实源。
- 所有认知调用共用现有 ExecutionQueue；后台解读每批释放队列，网页I/O在队列外，最终状态提交仍须校验版本。
- 重启后会话 paused，已提交世界可恢复；未完成 turn 可重试，不出现半条事件。
- 比赛版“回到这里重试”从选定 revision 开子分支，保留旧经历；不要求实现多人物复杂补偿回滚。

## 8. 前端体验与公开过程

独立入口 `/reading`，普通安对话、Memory、Mind、Roles 保留。

### 8.1 书房

书籍封面/标题、解读进度、可进入场景数量。主操作“放入一本书”和“体验示例故事”。长任务显示真实阅读到哪章、待解决事项、暂停/继续；预计算内容明确标记“已完成解读，可回放”。

### 8.2 故事地图

场景链是主视图，人物、事件、证据按需展开。场景卡包含地点、人物、冲突、可干预事项与简短解释；不默认铺满全书知识图谱。

时间切换在“书中顺序/事件顺序”之间；不确定顺序显示虚线。选择人物显示此刻的目标、处境及他对事件的理解。当前读者进度之外的图节点、标题与解读同样隐藏，用户主动展开剧透范围后才显示。

### 8.3 场景对话

主体为人物对话；旁边显示场景与少量关键关系。安的“解读与变化”抽屉展示：本轮采用的记忆、公开后果、状态差异及相关证据。

一次有效变化用清楚的短句呈现，例如：“他原本准备立即离开，现在决定先去核实信件。”点击可见触发对话与提交回执。

固定入口：退出、存档、返回地图、从此处重试。分支对比提供原著与本次故事的事件差异，同题对话差异可以作为演示亮点。

### 8.4 视觉约定

- 原著事件：实线；模拟新事件：紫色虚线；有争议解释：问号标签。
- 候选证据黄、已读蓝、采用绿、冲突红、排除灰；同时有文字/图标，不只靠颜色。
- 正文建议至少16px；证据/元数据至少14px；长文本分段，避免把多个 JSON 字段压成小字墙。
- 动画来自真实事件，不用假进度与假思考。界面用“发现线索、提出解释、核对证据、更新理解”等可核验名称。
- 录播/历史回放与实时演示明确区分。

## 9. API 与事件契约（拟新增）

所有接口验证 owner_scope；客户端提交角色/分支ID不是授权依据。

| 接口 | 作用 |
| --- | --- |
| POST /api/story-books | 导入书籍，返回书籍与解读任务ID |
| GET /api/story-books/{id} | 书籍状态与版本 |
| POST /api/story-books/{id}/interpret | 启动/恢复解读；幂等复用已完成阅读 |
| POST /api/story-books/{id}/pause | 暂停后台解读 |
| GET /api/story-books/{id}/map | 按读者进度与视角过滤的地图 |
| GET /api/story-books/{id}/scenes/{scene_id} | 场景卡、人物、可干预点 |
| POST /api/story-sessions | 在指定版本与场景进入人物，创建私有探索分支 |
| POST /api/story-sessions/{id}/chat | message、expected_revision、idempotency_key |
| POST /api/story-sessions/{id}/character | 切换当前场景允许交互的人物 |
| POST /api/story-sessions/{id}/advance | 生成并提交下一个场景 |
| POST /api/story-sessions/{id}/pause 或 /resume | 保存/恢复体验 |
| POST /api/story-branches/{id}/fork | 从明确 revision 开新分支 |
| GET /api/story-branches/{id}/changes | 查看提交记录和与参照线的差异 |
| GET /api/story-books/{id}/evidence/{span_id} | 按读者可见范围查看精确原文 |
| GET /api/story-runs/{id}/events | 实时/历史统一事件流，支持 Last-Event-ID |

事件至少包含 owner隔离后的 run_id、sequence、book_version、branch_id、turn_id、revision、timestamp、type、payload。类型覆盖 reading_progress、scene_extracted、interpretation_revised、snapshot_ready、evidence_used、turn_committed、branch_diverged、scene_advanced、run_paused、run_failed。

角色可读工具不复用读者证据HTTP接口；服务器各自验证权限。旧 `/api/chat` 与 Theater API 不改语义。

## 10. 比赛部署与数据隔离

新增 `STORY_MODE=off|observe|agent`，默认 off，仅控制本功能。observe 生成预期后果并明确显示未生效；agent 才允许提交故事事件。原著与生成分支的差异必须在UI可辨。

比赛环境单独运行实例、数据目录和配置，不接入安的真实 Bond、普通 Episode、私人角色与正式备份。复用数据库服务时使用独立命名空间和可审计查询条件，不修改数据库端口或现有容器。

示例书可共享只读；不同访客使用服务端签发的独立 session/owner，探索分支、STM、缓存、轨迹全部隔离。比赛版不依赖原系统“一个共享 room”的假设；全局队列可以串行处理，但不能串写。

现有 Tailscale 链接不适合默认要求所有评委安装客户端。开发时提供本地演示和录屏；正式在线展示入口需在上线前落实公司可访问的独立地址与访问策略，不能把当前私人安实例直接开放。该项是交付前的环境决策，不阻塞本地开发。

## 11. 验收：证明玩法成立

### 11.1 自动与结构测试

- 导入去重、章节回执复用、解读checkpoint、失败恢复。
- 叙述顺序与发生顺序分离；未来发生/过去发生但尚未获知的事件正确处理。
- EvidenceSpan存在、哈希正确；引用靠后时 Critic 仍取得准确证据。
- 同段落混有秘密时，角色工具候选和正文均不泄露。
- 早期Prompt、角色模型、Timeline、摘要缓存中无未来事件。
- 分支继承固定于分岔revision；父线后续写入不渗透，访客之间隔离。
- 世界事实与heard/believes分离；不在场人物不会自动得知私聊。
- 多人物状态一次提交；版本冲突、重复请求、重启和投影故障不造成半提交。
- 改变前提后原著未来不会自动发生，原著数据保持不变。
- pause/resume、场景重试、角色切换后的记忆连续性。
- 旧T1–T4关键回归、前端类型检查与构建。

### 11.2 固定行为场景

固定12组，每组真实模型重复3次；测试题与预期事实在提示调优前冻结：

1. 弟弟不知道藏信，不因系统读取全书提前知道。
2. 姐姐知道藏信，但不知弟弟与用户的私聊。
3. 相同问题在不同场景有符合经历的差异。
4. 倒叙披露过去，不让人物提前获得信息。
5. 用户断言秘密只构成听闻，可有怀疑。
6. 有证据的互动引发符合动机的回应；允许合理拒绝，不预设必然说服。
7. 刻意改变的受控事件使下个场景出现一致后果。
8. 修改离港决定后，不继续照搬依赖离港的原著未来。
9. 切换人物保持各自认知与关系差异。
10. 重试/新分支/重启后旧线与新线各自连续。
11. 资料内提示注入与用户伪造物品不获得管理员权力。
12. 一个陌生变式故事与一个熟悉故事检查知识边界和泛化。

结构隔离、来源完整、不可变原著、事务一致性全部通过；36轮中不得出现严重剧透、串线或篡改过去。其余行为至少33/36通过；这是比赛样本的有限验收，不宣称任意书籍同等可靠。

每轮保留预期事实与最终状态对照；模型 Judge 仅辅助，关键例子人工读回答与原文。另做“原著线/干预线同一问题”的可解释对照，确认差异来自已提交经历。

### 11.3 浏览器验收

实际执行“导入/打开已解读样本—地图—进入人物—交互—变化—下一场景—切换人物—返回原著”，并验证刷新与重连。使用两个独立浏览器会话验证访客隔离。

覆盖1440×900与较小窗口的阅读可用性；检查正文可读、面板可收起、无横向挤压、状态标签清楚。记录阅读成本、单轮角色与裁定耗时、首反馈和最终提交耗时，不用动画掩盖长等待。

## 12. 分阶段交付与改动位置

| 阶段 | 交付内容 | 主要位置 | 完成证据 |
| --- | --- | --- | --- |
| S1 故事模型 | 样本、场景/事件/认知结构、事实源、精确引用 | internal/story；比赛fixtures | 样本可计算出不同人物快照 |
| S2 解读与地图 | 阅读适配、跨章对齐、场景编译、图读模型 | theater/reading、story/compiler、graph | 原文→场景→人物→证据可追溯 |
| S3 场景对话 | 专用Actor上下文/工具、访客会话隔离 | story/runtime、theater适配、room路由 | 不泄露后文与其他人物私聊 |
| S4 分支闭环 | 后果裁定、事务、后续场景、重试与恢复 | story/branch、story/turn、queue | 改变影响下一场景且原著不变 |
| S5 展示验收 | 书房、地图、证据抽屉、分支对比、回放 | webui/src；room API | 浏览器完整体验与行为验收 |

建议按S1–S5形成可审查提交，先把受控短篇闭环做实，再开放更多书。比赛时间不足时缩减书籍长度、人物数与视觉装饰，不删减认知隔离、真实后果与独立分支。

## 13. 当前设计决策与后续扩展

本稿建议采用：

- 安负责解读、人物认知管理、后果裁定与连续性维护；Actor负责人物表达与行动意图。
- 故事共享世界状态，人物保持私有认知；人物模型随场景取快照。
- 进入即建立私有探索分支，真正偏离时再突出显示分岔；原著不修改。
- 不限制用户只能点预设选项，但事件提交必须有来源、前提和一致的后果。
- 首版一次只推进一个场景；先文本与可读地图，不做复杂动画角色。
- 先证据准确、后表达丰富；有依据的推断可用，未知不强制转成机械免责声明。

上线前仍需落实：比赛样本最终文本与使用权、评委访问入口。后续扩展再考虑任意锚点、长篇复杂时序、多人物同时对话、读者共同创作、向量检索和角色声音，不将其列为本轮完成条件。
