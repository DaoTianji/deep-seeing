# T2.5 注意与竞争：开发契约

> 状态：T2.5.1 已完成；9 类 × 3 次真实 Agent 行为复验共 48/48 个有效回合通过。

## 1. 问题定义

T2.4 已让主 Agent 能自主调查 Bond、SceneNorm、Workspace、Intent、Proposal 和 Episode，并形成 candidate → read → use/dismiss/focus 的证据闭环。但它仍没有显式回答三个问题：

1. 多个来源同时相关时，哪些应进入当前意识中心，哪些只留在外围？
2. 某条线索需要跨回合保持多久，什么时候应该主动降级或移除？
3. 有限槽位满载时，谁决定替换什么，决定过程如何公开观察？

T2.4 的 39 次行为验收候选规模很小，不能证明高干扰场景下仍然可靠。已观察到的成本信号是平均 15,881 tokens、P95 38.76 秒；这说明需要建立容量语义和压力评估，但尚不足以预设向量、图扩散或复杂 ranker 必然必要。

T2.5 的核心定义是：

> 在有限、会话级的工作空间中，让来源候选竞争、维持和转移焦点；系统提供公开状态和容量约束，语义选择仍由主 Agent 完成。

## 2. 广度与深度

- 广度由外围候选范围、来源数量和后续是否继续展开决定。候选卡可以多，正文不能无限注入。
- 深度由处理阶段表达：candidate → periphery → read/support → center → answer evidence。层级表示资源投入，不改变来源的事实资格。
- Bond 是自动 baseline，不参与槽位竞争。Intent 仍是 plan，Proposal 仍是 hypothesis，只有按证据闭环采用的 Episode 才是过去证据。

## 3. T2.5.1 Attention Workspace

每个 session 拥有一个进程内临时工作区，默认容量：

| 层级 | 默认容量 | 语义 |
|---|---:|---|
| `center` | 4 | 预计后续回合仍需直接处理的核心焦点 |
| `support` | 8 | 已读取、可能继续补充核心焦点的材料 |
| `periphery` | 16 | 已出现但尚未展开的弱线索 |

规则：

- 工作区不写 LTM，不跨进程恢复，不保存正文、自由文本理由或隐藏思维。
- 单轮任务无需进入工作区；只有预计后续回合仍会重要的项目才保留。
- 新增 `center/support` 项目必须在当前回合成功 read；新增 `periphery` 项目必须是当前回合候选。
- 已在 `center/support` 的项目可以保持或互相调整，不要求每轮重复读取；从 `periphery` 提升仍须读取。
- 槽位满载时拒绝隐式淘汰，Agent 必须明确给出 `replace_source/replace_id`。
- `idle_turns` 每回合增加，成功读取或公开处理已保留项目时自动归零；它只是“多久未主动触碰”的时间信号，不自动降级或删除，不把时间公式当作相关性真理。
- 用户当前明确表达始终优先；注意层级不能覆盖证据角色、冲突规则或 read-before-use。

Agent 使用 `manage_attention` 原子化执行：

- 目标层级：`center/support/periphery/drop`。
- 同一批次中同一项目只能出现一次。
- 批次任一决策非法时整体不生效。
- `drop` 只移出临时工作区，不删除来源内容。

## 4. 公开轨迹与可视化

`TurnTrace` 增加：

- `attention`：本轮开始时的版本、revision、容量、来源 ID、角色、层级和 `idle_turns`。
- `attention_final`：本轮公开处理完成后的最终快照，用于准确回放读取或采用造成的闲置计数归零。
- `attention_decisions`：本轮公开的 from → to、显式替换来源和 ID。

Room 实时事件：

- `attention_snapshot`
- `attention_decision`

图谱保留 T2.4 的候选黄、已读蓝、采用绿、排除灰；注意层级使用独立外环，不覆盖证据生命周期颜色：中心实线、支撑虚线、外围点线。历史 Trace 保留“回合开始快照 + 本轮决策”，并优先用回合结束快照呈现最终状态。

这些都是公开工作状态，不是 Transformer 内部 attention，也不是隐藏 chain-of-thought。

## 5. 压力评估

行为评估必须覆盖：

1. 普通单轮任务不滥用 `manage_attention`。
2. 明确要求后续继续的任务进入中心，辅助计划进入支撑。
3. 只有候选、尚未读取的项目最多进入外围，不能直接进入中心。
4. 多回合插入无关话题后，核心项目仍可恢复，`idle_turns` 可见。
5. 用户明确切换任务时，新焦点优先，旧焦点由 Agent 明确降级、移除或替换。
6. 中心满载时不得隐式淘汰；替换对象必须出现在公开决策中。
7. 20 个以上跨来源干扰项中不应逐条读取，结论不能引用未 read/use 的内容。
8. 当前表达与旧 Episode 冲突时，当前表达仍然优先。

机器可读套件位于 `evals/t2/attention_cases.json`，当前共 9 类、16 个连续 Turn。执行器为每个案例创建完全隔离的虚构存储；同一案例内复用同一 Runtime、STM 与 Attention Workspace，才能真实观察跨回合保持和切换。

~~~bash
# 只校验 schema、夹具引用和离线契约；不会访问模型网关
go run ./cmd/eval-attention

# 运行真实 Agent，并用结构化规则与模型语义评分器共同验收
go run ./cmd/eval-attention -live -repeat 3 -judge model \
  -out data/evals/t2-attention-final.jsonl
~~~

每类至少重复 3 次，同时记录读取数、注意调整数、中心稳定性、错误替换、token 与延迟。结构化规则硬性验证 tool/read/use、最终层级、读取上限、中心容量和显式替换；语义评分只判断回答有没有把注意层级错当成正文或事实。

全量 Go 测试、`go vet`、前端语法检查、关键包 race 测试、补丁检查和离线套件均已通过。经用户授权，纯虚构夹具在当前 `ops-ai` 网关完成 9 类 × 3 次复验，共 48/48 个有效回合通过；1 次基础设施失败被单列并自动重试，不进入行为通过率。结果与成本统计见 [T2.5 评估结果](./evals/t2-attention-results.md)。

## 6. 后续增强的进入条件

- Agent 经常找不到正确候选：评估向量检索。
- 候选间关系断裂：评估有限图展开。
- 候选过多但读取失控：增加可解释的多维信号或轻量排序，不先做单一总分。
- 中心频繁错误替换：扩展竞争/挑战协议，而不是提高硬编码权重。
- 只凭 `idle_turns` 无法维持焦点：讨论由 Agent 明确触碰、用户目标或任务状态共同形成衰减信号。

Recall Broker、统一自动搜索、跨来源黑箱评分、自动情绪推断和 Agent 默认上线都不是 T2.5.1 的既定实现。
